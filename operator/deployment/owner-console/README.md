# Локальный интерфейс подписи владельца

Этот интерфейс продолжает сохранённый запрос полного Devnet-выпуска. Он доступен
только на `127.0.0.1` компьютера оператора. Основной сайт и лабораторный RPC не
используются для хранения ключей или подписей. Приватный ключ кошелька владельца
остаётся в кошельке; пароль от зашифрованного bundle вводится только в терминале.

## Подготовка и запуск

Нужны Node 24.19, закреплённые зависимости корня/`operator`, существующий реальный
bundle и отдельный приватный Devnet RPC. Реальные bundle и endpoint ещё не
созданы этим изменением. Сначала завершаются custody и настройка gateway из PR31.
Не использовать адреса тестовых fixtures и не повторять старый лабораторный mint.

```sh
node operator/deployment/owner-console/build.mjs
node operator/deployment/owner-console/cli.mjs prepare private/DEPLOYMENT collection-create
node operator/deployment/owner-console/cli.mjs serve private/DEPLOYMENT
```

`prepare` запрашивает пароль без эха, проверяет vault, выполняет preflight и
unsigned simulation, создаёт только частичные подписи новых аккаунтов и сохраняет
запрос до возврата результата. Режима автоматического retry здесь нет. Если
запрос уже существует, новый не создаётся. Конфигурация RPC берётся из приватных
`COOLBEARS_RPC_URL` и, для gateway, `COOLBEARS_OPERATOR_RPC_TOKEN`.

`serve` не расшифровывает vault и не просит пароль. Он печатает приватную ссылку
только в локальный TTY, слушает порт 8788 исключительно на IPv4 loopback и
закрепляется за одной сохранённой попыткой. Ссылку с capability во фрагменте
нельзя пересылать или публиковать. Фрагмент не передаётся в HTTP-запросе; API
получает credential отдельным заголовком. После перезапуска ссылка меняется.
Основной сайт и публичный хостинг не должны публиковать каталог `owner-console`.

Подключение кошелька и подпись требуют отдельных явных нажатий. Отбираются только
Wallet Standard кошельки с `solana:signTransaction`, Devnet и v0; адрес аккаунта
и его public key должны совпасть с владельцем запроса. Вызов
`signAndSendTransaction` и другие способы отправки отсутствуют. Wallet Standard
тип `SolanaSignTransactionInput` проверен по закреплённой установленной библиотеке.

## Однократная выдача и восстановление

Перед выдачей bytes выполняется новая unsigned simulation именно сохранённого
запроса. Blockhash не заменяется. Затем журнал атомарно сохраняет `request-wallet`
с claim ID, и лишь после этого возвращаются данные для кошелька. Другая вкладка,
профиль, процесс или перезапущенный сервер не может повторно получить разрешение
на подпись занятой попытки. Истечение времени само по себе claim не снимает.

Перед вызовом кошелька браузер проверяет IndexedDB и сохраняет локальную запись
ожидания. Явный отказ кошелька с кодом 4001 передаётся серверу с точным claim ID;
событие `wallet-declined` освобождает выдачу для следующего ручного нажатия. Это
зафиксированный ответ доверенного локального интерфейса, не доказательство
ошибки/отсутствия транзакции в блокчейне. При потере ответа или неизвестной ошибке
claim остаётся; автоматической очистки или повторной подписи нет.

Полученный ответ проверяется в браузере и независимо на сервере: тот же message,
те же signers и все исходные частичные подписи, действительная подпись владельца.
Затем он сохраняется в IndexedDB и отправляется только в локальный файловый
журнал. Потерянное подтверждение записи восстанавливается идемпотентно, без новой
подписи и без второго события `signed`. Сервер подтверждает запись после чтения
сохранённого журнала. Поздний правильный ответ в состоянии `unknown` сохраняется
как `unknown`; это не разрешение отправить или повторить транзакцию.

Если браузер не может сохранить данные уже после получения подписи, ответ
остаётся в памяти и сначала предпринимается запись в локальный журнал. При
неудаче доступна загрузка приватного JSON. Импорт такого сохранённого файла:

```sh
node operator/deployment/owner-console/cli.mjs import-response private/DEPLOYMENT /absolute/private/response.PRIVATE.json
```

Импорт не требует RPC, пароля или повторного открытия кошелька. Он принимает
только подпись текущего сохранённого запроса и повторно проверяет все bytes.
Файл читается как ограниченный regular file без следования симлинку. Существующий
журнал не заменяется. Browser storage, неподтверждённые операции и история не
очищаются. Оригинальный bundle и его копию одновременно запускать нельзя.

## Границы

- HTTP Host/Origin/Fetch Metadata проверяются до доступа к bundle; каждый API
  защищён случайным 256-bit capability. Нет wildcard CORS, iframe, внешних скриптов,
  передачи RPC-ключа в браузер или API чтения vault.
- POST JSON ограничен 4 KiB/4 s. Сервер отдаёт только три встроенных статических
  ресурса и фиксированные API; пути filesystem из URL не используются.
- Это локальная POSIX-система для desktop extension wallet, не удалённая панель
  и не готовый мобильный deeplink. Телефон не может подключиться к loopback
  другого компьютера. Реальные Phantom/Solflare и физические устройства ещё
  требуют отдельной проверки после приватной настройки.
- Сохранённая подпись не гарантирует, что blockhash ещё действителен. Перед будущей
  отправкой обязательны signed simulation, проверки журнала/сети и завершённый
  sender. Ни эта панель, ни CLI не выполняют broadcast, Mainnet или открытие продаж.
- Журнал с новыми событиями `request-wallet`/`wallet-declined` нужно читать кодом
  PR32 или новее. Старый код не должен перезаписывать такую историю.

Проверки: `deployment-owner-console.test.mjs` (реальный loopback HTTP, журнал и
синтетический кошелёк), `deployment-owner-console.browser.mjs` (Chromium, настоящие
DOM/IndexedDB и подменённый Wallet Standard), прежние signing/handoff/journal
тесты. Браузерный job публикует отчёт и снимки desktop/mobile layout. Эмуляция
макета телефона не является проверкой физического кошелька.

Источники: [Wallet Standard Solana extension](https://github.com/wallet-standard/wallet-standard/blob/master/extensions/solana.md),
[Phantom SignTransaction](https://docs.phantom.com/phantom-deeplinks/provider-methods/signtransaction),
локальные типы `@solana/wallet-standard-features/lib/types/signTransaction.d.ts`.

## Явный повтор PR34

После сохранённого `failed` из `send-cli.mjs review-failure` используется
`cli.mjs prepare-retry <bundle> <step>`. Это отдельная ручная команда с новым
preflight, новым blockhash и вводом пароля в TTY. Подключение и подпись снова
выполняются явно; отправку панель не делает. Обычный `prepare` повтор не начинает.
Полный порядок и границы — [RETRY.md](../RETRY.md).
