# PR34: ручной повтор после окончательной ошибки

Продажи закрыты, цена 0,2 SOL. Этот этап продолжает PR33. Код не развёрнут,
реальные приватные bundle/endpoint пока не настроены. Тесты используют
одноразовые ключи и перехваченные HTTP-ответы, без реальных транзакций.

## Что разрешает повтор

Только **finalized execution failure** точной сохранённой транзакции:

1. Клиент заново проверяет весь bundle и canonical manifest, текущую попытку и
   подписи. На Devnet запрашивает историю signature и finalized transaction.
2. Оба ответа должны подтверждать одну finalized-транзакцию: одинаковый slot,
   одинаковая ненулевая ошибка, те же полные wire bytes и подписи. `confirmed`,
   `null`, противоречивые старые поля `status`, другие bytes и 429 не подходят.
3. Все аккаунты и полный префикс config lines должны соответствовать состоянию
   **до** неуспешного шага, в finalized bank не раньше receipt. Это проверяет
   отсутствие его ожидаемого результата. Комиссия за неуспех не возвращается.
4. Явная команда отправляет сохранённые bytes в отдельный метод приватного
   gateway `coolbears_authorizeFailedRetry`. Метод не передаётся в Helius и не
   отправляет транзакцию. Сервер сам проверяет утверждённую message identity,
   все подписи, точный текущий claim и Devnet genesis; затем **сам** запрашивает
   оба receipt. Клиентские флаги finality/absence сервер не принимает.
5. SQLite сохраняет неизменяемое доказательство, связанное с предыдущими
   identity/signature/transaction hash/slot. Текущий claim не удаляется.
6. Только совпадающий ответ сервера и неизменный журнал позволяют CAS-запись
   `failed`. Следующий шаг — отдельная ручная подготовка новой попытки.
7. Новая подготовка повторяет preflight/fee/balance/unsigned simulation, требует
   пароль vault в локальном TTY и **новый blockhash**, не использованный ни одной
   прежней подписанной попыткой этого шага. Затем владелец отдельно подписывает.
8. Sender PR33 опять выполняет signed simulation и сохраняет claim до отправки.
   Gateway атомарно заменяет текущий указатель, только если его предыдущая
   попытка имеет собственное доказательство failed. Ранее использованная
   signature запрещена навсегда. Конкурирующий отправитель не получает вторую
   попытку. Доказательство прежней попытки не освобождает новую.

В SQLite сохраняются прошлые claims, signatures, failure proofs и дневной
ledger. Чтение всех прошлых подписей остаётся разрешённым после нового claim и
restart. Старые PR33 claims без отдельной history-записи поддерживаются: при
первой замене они также сохраняются. Нет очистки, TTL или сброса по таймеру.
Каждый реальный upstream-вызов списывается по прежним квотам; proof reuse не
делает upstream-вызов и не изменяет квоту.

## Команды после реальной приватной настройки

Сначала обычное восстановление успешного результата:

```sh
node operator/deployment/send-cli.mjs resume private/DEPLOYMENT collection-create
```

Для осознанной проверки неуспеха и разрешения нового запроса:

```sh
node operator/deployment/send-cli.mjs review-failure private/DEPLOYMENT collection-create --authorize-retry
```

Эта команда только проверяет и сохраняет результат. Она **не** создаёт подпись,
не отправляет транзакцию и не начинает новую попытку. Только после `failed`:

```sh
node operator/deployment/owner-console/cli.mjs prepare-retry private/DEPLOYMENT collection-create
node operator/deployment/owner-console/cli.mjs serve private/DEPLOYMENT
```

Владелец вручную подключается и подписывает новый запрос. После сохранения
ответа — отдельный `send-one ... --devnet-send`, затем `resume`. Команды требуют
приватные `COOLBEARS_RPC_URL`/`COOLBEARS_OPERATOR_RPC_TOKEN`. Секреты не передавать
в аргументах, чате, отчётах или публичном frontend. Лабораторию 2/2 не повторять.

## Сбой между сервером и локальным журналом

Если proof уже записан, но HTTP-ответ потерян или CAS/fsync не подтвердился,
повторить **только review-failure той же попытки**. Gateway возвращает сохранённое
разрешение, пока именно этот claim текущий. Клиент заново проверяет receipt и
аккаунты; он не подписывает и не рассылает старые bytes. Если `failed` уже есть в
локальном журнале, возвращается `already-recorded` без обещания свежего чтения.

Если сервер уже занят другой попыткой, старый review получает 409. Если изменён
журнал, найден неизвестный результат, изменилась сеть, испорчено хранилище или
получен 429, операция остаётся остановленной. Ни один из этих случаев не
разрешает очищать lock/storage, запускать старую копию bundle или обходить claim.

## Что ещё не готово

- **Expired/отсутствующая транзакция:** истёкший hash и нулевой receipt не доказывают,
  что транзакция ранее не выполнилась. Проверки полной истории адресов и
  безопасного разрешения такого повтора здесь нет. Отсутствующий server claim
  также не создаётся задним числом. Такие случаи остаются заблокированы.
- Нет автоматической очереди, повторной отправки, Mainnet или открытия продаж.
- Реальная приватная настройка, свежий бюджет, реальные кошельки/телефоны и
  публичный процесс покупки 1–50 — отдельные незавершённые участки.
- RPC остаётся доверенным источником finality. Два согласованных ответа одного
  провайдера — проверка согласованности, а не независимый consensus proof.
