# Зашифрованные подписанты и передача запроса владельцу

Этот этап добавляет локальное хранение ключей **новых** collection, reserved asset #0000 и Candy Machine. Ключ кошелька владельца не создаётся, не импортируется и не хранится. Guard выводится как PDA и отдельного ключа не требует. Реальный production-bundle ещё не создан; тесты используют временные ключи и каталоги.

## Состав bundle

| Файл | Содержимое |
| --- | --- |
| `vault.json` | Три зашифрованных seed по 32 байта и параметры проверки целостности; открытых приватных ключей нет. |
| `journal/manifest.json` | Полный canonical план, неизменяемые публичные адреса и ожидаемые результаты всех 1431 шагов. |
| `journal/` | Сохранённые попытки, запросы, подписанные ответы и цепочка событий. |
| `READY.json` | Привязка готового bundle к хешам vault и manifest. Появляется последним. |

Каталог создаётся заново с режимом `0700`, файлы — `0600`, с записью и синхронизацией на диск. Существующий каталог не перезаписывается. Незавершённое создание сохраняет имеющиеся файлы, но bundle без корректного `READY.json` не допускается к работе. Символические ссылки и небезопасные разрешения внутри bundle отклоняются. Это реализация для локальной POSIX-файловой системы; поведение синхронизируемых папок и Windows ACL не проверено.

Все три seed шифруются AES-256-GCM. Для каждого vault создаются новые случайные salt 32 байта и IV 12 байт; authentication tag — 16 байт. Ключ шифрования выводится из парольной фразы через scrypt с фиксированными `N=32768`, `r=8`, `p=1`, `maxmem=64 MiB`. ID, сеть, хеш manifest и параметры заголовка входят в authenticated data. Подмена ciphertext, tag, заголовка или manifest блокирует открытие. После расшифровки дополнительно сверяются публичные адреса трёх seed и полный canonical SDK-план.

Парольная фраза должна быть новой и непредсказуемой, сохранённой отдельно от bundle. Допустимый размер 16–1024 байта — только техническая граница, не оценка стойкости пароля. Потеря парольной фразы или vault не исправляется одними публичными адресами. Не использовать seed-фразу Phantom как пароль. Обнуление рабочих буферов выполняется по возможности; JavaScript, криптобиблиотека и ОС могут сохранять внутренние копии памяти.

## Локальные команды

После установки закреплённых зависимостей оператора:

```sh
node operator/deployment/custody.mjs init private/NEW_DEPLOYMENT private/deployment-options.json
node operator/deployment/custody.mjs inspect private/NEW_DEPLOYMENT
node operator/deployment/custody.mjs verify private/NEW_DEPLOYMENT
```

`init` принимает отдельный JSON **публичных параметров** с ровно пятью полями: `id`, `cluster`, `blockhash`, `lastValidBlockHeight`, `machineRentLamports`. Типы и ограничения описаны в [плане deployment](README.md). Значения blockhash и rent не берутся из старой лаборатории или произвольного примера: их свежая проверка и полный расчёт бюджета остаются отдельной работой. Сам `init` не обращается в сеть и не доказывает актуальность параметров.

Пароль вводится только в локальном терминале без отображения символов, при `init` — дважды. В аргументах команды, JSON, переменной окружения и чате пароль не передаётся. `inspect` показывает публичные адреса и состояние журнала без расшифровки. `verify` запрашивает пароль, проверяет расшифровку и соответствие ключей адресам, затем закрывает доступ к seed. Ни одна из этих команд не подписывает owner-транзакцию и не отправляет её.

Для резервной копии остановить все процессы, использующие bundle, скопировать **весь каталог** с сохранением приватных разрешений на отдельный носитель и выполнить `verify` для копии. Сохранить отдельно последние `manifestSha256`, revision и headHash из `inspect`. Старые резервные копии могут не содержать поздние попытки: перед восстановлением нужно сверить сохранённую вершину журнала и результат операций в сети. Не запускать исходный каталог и копию одновременно. Не создавать новый bundle вместо потерянной истории уже начатого deployment.

Приватные bundle размещаются под исключённым из Git каталогом `private/`. Автоматическая облачная копия, восстановление незавершённого каталога, смена парольной фразы и доказательство отсутствия удалённого конца журнала этим этапом не реализованы.

## API и порядок подписи

| API | Результат |
| --- | --- |
| `createDeploymentSignerVault({id,cluster,blockhash,lastValidBlockHeight,machineRentLamports,passphrase})` | Создаёт три случайных signer, canonical manifest и зашифрованный vault; `passphrase` — `Uint8Array`/`Buffer`. |
| `createDeploymentBundle({directory,manifest,vault})` | Сохраняет новый закрытый bundle; возвращает `{vault,journalDirectory,snapshot}`. |
| `readDeploymentBundle(directory)` | Проверяет готовность, привязки, canonical intent и журнал; пароль и правильность расшифровки не проверяет. |
| `openDeploymentSignerVault({vault,manifest,passphrase})` | Возвращает только `partialSign` и `dispose`; экспорта приватных ключей нет. |
| `prepareDeploymentSigning({directory,stepId,passphrase,endpoint,...})` | Сам запускает preflight и unsigned-симуляцию, создаёт частичные подписи новых accounts и сохраняет `prepare` до возврата запроса. |
| `readPendingDeploymentSigning(directory)` | Возвращает уже сохранённый `wallet-pending` запрос без изменения bytes и без RPC. |
| `acceptDeploymentSigningResponse({directory,request,response})` | Проверяет ответ владельца против точного сохранённого запроса и записывает событие `signed` до возврата результата. |

`partialSign({stepId,transactionBase64,lastValidBlockHeight,attempt})` принимает только полностью неподписанный canonical message текущего плана; допускается обновление recent blockhash. Подписываются только соответствующие новые accounts. Подпись владельца остаётся пустой. Подмена instruction, payer, account, signer или уже существующая подпись отклоняется. После `dispose()` новые подписи недоступны.

Handoff использует собственный вызов read-only preflight и unsigned-симуляции; входного JSON с флагом «проверено» недостаточно. Перед сохранением сверяются manifest, revision и вершина журнала. Повторный запрос требует явного `retry: true` после разрешённого состояния; активная попытка не пересоздаётся. Ответ кошелька должен сохранить все bytes сообщения и частичные подписи. Поздний корректный ответ для `unknown` сохраняется с прежним состоянием `unknown`, без автоматической отправки или перехода дальше.

Возвращённый запрос — заготовка для будущего интерфейса кошелька. Программа не вызывает Phantom, не реализует пакетную подпись и не гарантирует срок blockhash. `readPendingDeploymentSigning` — восстановление bytes, а не разрешение повторно показать окно кошелька без проверки предыдущей попытки. Подписанный ответ и `unknown` требуют сверки результата. До будущей отправки нужны свежая проверка, симуляция и отдельный `claim-send`.

`prepareDeploymentSigning` теперь возвращает `simulationVerified=true` с `simulationMode=unsigned` после успешной симуляции именно его сообщения. Восстановление запроса и приём подписи не переиспользуют этот результат как свежую проверку. `readyToSubmit=false` и `budgetComplete=false` сохраняются. [Модель бюджета и signed-симуляция](BUDGET.md) подготовлены; свежая live-оценка, сетевой отправитель и доказательства `failed`/`expired` ещё предстоят. Завершение custody не открывает продажи и не подтверждает Mainnet deployment.

Основа криптографического формата: [Node.js crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html); ввод без отображения — [Node.js TTY](https://nodejs.org/docs/latest-v24.x/api/tty.html). Проверки этого этапа используют реальные SDK-байты и подписи тестовых ключей, но синтетические RPC-ответы; это не результат испытания кошелька владельца на телефоне.
