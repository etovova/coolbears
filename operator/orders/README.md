# Офлайн-планировщик заказов CoolBears

`transactions.mjs` готовит неподписанные шаблоны Core Candy Machine, а
`journal.mjs` моделирует журнал заказа на 1–50 NFT. Эти две части остаются
офлайн. Отдельный [preflight](PREFLIGHT.md) теперь проверяет сеть, закрытый
guard, остаток, частичную стоимость и unsigned simulation первого item нового
заказа. Он не подключён к сайту/кошельку и не создаёт ключей, подписей или
транзакций в сети. Продажи остаются закрытыми; готовность к Mainnet не заявляется.

## Что планируется

`transactions.mjs` использует установленный официальный SDK `@metaplex-foundation/mpl-core-candy-machine` и `mintV1` через Candy Guard. На каждый ещё не завершённый item создаётся отдельная транзакция v0 с лимитом сериализованного размера 1232 байта. Покупатель — fee payer, payer, minter и получатель NFT; второй требуемый подписант — отдельный asset. Подписи в шаблоне пустые. Вызовы RPC, HTTP, генерации ключей и подписания внутри контекста планировщика заблокированы.

Поля `quantity` и `availableAtPlanning` описывают переданный снимок наличия. Они не резервируют NFT и не подтверждают актуальный остаток. `items[].index` — позиция в заказе, а не номер выбранного NFT: будущая машина распределяет metadata согласно своей конфигурации. Резервный #0000 не входит в продажи; ожидаемые скрытые metadata относятся к #0001–#9999.

Цена 0,2 SOL на item и адрес treasury берутся из политики проекта. `payment.lamports` и итоговые суммы — ожидаемая цена, а не доказательство цены в сети. Сумма Sol Payment хранится в Candy Guard; в mint-инструкции указывается адрес получателя. Будущий адаптер обязан проверить guard и его условия перед подписью. Текущий шаблон использует default guards без выбора группы и не реализует дополнительные guard-сценарии.

Результат `buildOrderTransactions` содержит `mode: 'offline-unsigned-order'`, `guardPriceVerified: false`, `blockhashVerified: false`, `networkVerified: false`, `feeQuote: null`, а также нулевые счётчики сетевых запросов, подписей и отправок. `summarizeOrder` возвращает `readyToSubmit: false` и `feesAndRentQuoted: false`. Переданные cluster и blockhash проверяются по формату; принадлежность сети, срок действия и баланс не проверяются.

Заказ на несколько NFT не атомарен: это несколько независимых транзакций. После успешной части заказа оставшаяся часть может остановиться. Итоги по указанной цене не учитывают rent, сетевые комиссии, приоритетную комиссию или стоимость неудачных попыток. Внутри отдельной транзакции инструкции выполняются атомарно; это свойство не распространяется на весь заказ. [Solana: Transactions](https://solana.com/docs/core/transactions).

## API и хранение

| Функция | Назначение |
| --- | --- |
| `createOrder({ id, cluster, buyer, machine, collection, guard, quantity, available, assets })` | Создать пустой журнал с фиксированными адресами assets и revision 0. |
| `validateOrder(order)` | Проверить структуру, политику, уникальность адресов/подписей и допустимость истории. |
| `buildOrderTransactions(order, { blockhash, lastValidBlockHeight, retry: false })` | Получить неподписанные шаблоны; журнал не изменяется. |
| `transitionOrder(order, event)` | Получить следующую копию журнала; `event.revision` должен совпадать с текущим. |
| `saveOrder(storage, order, expectedRevision)` | Проверить предыдущую запись и сохранить следующую revision с проверкой чтением. При первом сохранении используется `null`. |
| `readOrder(storage, id)` | Прочитать и проверить сохранённый журнал. |
| `nextAction(order)` / `summarizeOrder(order)` | Определить следующий шаг модели и количество подтверждённых items. |

`storage` должен предоставлять синхронные `getItem`/`setItem`. Ключ записи — `coolbears:offline-order:v1:<id>`. Журнал содержит публичные адреса, ожидаемые message hashes, подписи и нормализованные результаты проверки; приватных ключей и подписанных байтов в нём нет. Ошибка сохранения или чтения должна останавливать будущий исполнитель до любых внешних действий.

Это модель **одного писателя**. Проверка revision и чтение после записи не являются атомарным compare-and-swap между вкладками или процессами. Для реального исполнителя ещё нужна исключительная блокировка; её нельзя заменить повторным вызовом `saveOrder`. Журнал также не является криптографически защищённым хранилищем.

## Порядок будущего исполнения

Сейчас перечисленные события только меняют офлайн-модель. Будущий исполнитель должен выполнять внешние действия строго после успешного сохранения соответствующего состояния:

1. `prepare` сохраняет `wallet-pending` с номером попытки, asset, blockhash, сроком действия и SHA-256 исходного сообщения **до** запроса подписи.
2. После проверки возвращённого сообщения и подписей `signature` сохраняет известную подпись. Обычный ответ переводит `wallet-pending` в `signed`.
3. `claim-send` переводит `signed` в `sending`; сохранить этот переход нужно **до** единственной отправки. Повторный `claim-send` из `sending`, `submitted` или `unknown` запрещён.
4. `submitted` фиксирует ответ отправителя, но не подтверждает создание NFT. `unknown` сохраняет неопределённый исход; он требует чтения и сверки, а не новой подписи или автоматического retry.
5. `reconcile` завершает попытку только по проверенным данным: `verified`, `failed` либо `expired`. Подтверждённые items исключаются из нового плана, история остальных сохраняется.

После перезагрузки `nextAction` направляет любую активную попытку (`wallet-pending`, `signed`, `sending`, `submitted`, `unknown`) на `reconcile`. Нельзя трактовать потерю ответа как отсутствие транзакции. Поздняя подпись для последней `unknown` попытки дополняет evidence, сохраняя `unknown`; отправку она не разрешает. Устаревшая revision требует повторного чтения и проверки актуальной попытки, а не перезаписи более нового журнала.

Событие `cancelled` предназначено для явного отказа до получения подписи и ставит весь заказ на паузу. Таймаут, закрытие вкладки и неопределённый ответ кошелька не доказывают отмену. После отмены требуется `resume`, затем отдельный явный `retry: true` для планирования и `prepare`. При `failed`/`expired` также требуется явный retry. Asset остаётся прежним, новая попытка добавляется после старой; его нельзя молча заменить новым адресом.

Сохранение приватного подписанта каждого asset и его восстановление пока не реализованы. Одного публичного адреса в журнале недостаточно, чтобы подписать повторную попытку после перезагрузки. Отдельное архивирование поздних ответов уже завершённых или предыдущих попыток тоже относится к будущему live-адаптеру: текущий `signature` обслуживает только последнюю `wallet-pending`/`unknown` попытку.

## Граница доверия evidence

`reconcile` принимает нормализованный объект proof. Проверка его структуры не доказывает факт в блокчейне. Будущий доверенный адаптер должен самостоятельно получить finalized-данные из нужной сети, проверить идентичность транзакционного сообщения и его SHA-256, signature, blockhash, machine/collection/buyer/asset, а затем сформировать proof.

Для `verified` нужны успешный finalized-результат и правильный Core account, владелец, коллекция и скрытые metadata. Для `failed` — finalized-ошибка выполнения и отсутствие ожидаемого asset. Для `expired` — доказанный выход за срок blockhash и согласованные проверки отсутствия подписи, asset и истории адреса. Ошибка RPC, пустой ответ одного запроса или таймаут таким доказательством не являются.

Проверять только успешный статус транзакции недостаточно: некоторые конфигурации Candy Guard, например Bot Tax, могут завершить транзакцию без создания NFT. [Metaplex: Minting from a Core Candy Machine](https://www.metaplex.com/docs/smart-contracts/core-candy-machine/mint).

## Проверки и следующий этап

Офлайн-тесты находятся в `operator/tests/order-*.test.mjs`; общая команда из каталога `operator` — `npm run verify`. Их область — модель журнала, сериализация настоящим SDK и декодирование шаблонов. Это не проверки кошельков, телефонов, RPC, попадания транзакций в сеть или покупки 50 NFT.

До подключения к сайту остаются отдельный production deployment, проверка актуального состояния/цены/наличия и бюджета, безопасное хранение asset signers, исполнитель с блокировкой и ограниченными ожиданиями, адаптер finalized evidence и восстановление частичных заказов. План полного выпуска и сохранения закрытых продаж: [PRODUCTION_READINESS.md](../PRODUCTION_READINESS.md).
